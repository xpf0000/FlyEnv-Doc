# FlyEnv 流量增长执行方案（SEO 延迟验证版）

> 基于 `task/chat1.md` 的诊断与当前仓库情况制定。
> 制定日期：2026-08-25
>
> 这是一份“先评审、后执行”的策略方案，暂不包含代码改动。

## 1. 核心判断

SEO 本身无法立刻证明成败，因此不能把 FlyEnv 的增长全部押在“持续写文章、等待 Google 排名”上。

我会把增长拆成四个互相验证的部分：

```text
搜索需求验证 → 内容/页面 → 多渠道分发 → 下载与使用转化
       ↑                                      ↓
       └────────────── 数据反馈 ──────────────┘
```

- SEO 负责长期积累和复利。
- 分发渠道负责在 Google 排名之前提供即时访问。
- 首页和项目页转化优化负责尽快验证卖点是否成立。
- GA4 + Search Console 负责判断“没有流量”究竟是没有需求、没有曝光，还是页面转化差。

## 2. 执行假设

本方案按以下条件设计：

- 主要由 1 名负责人推进，每周投入约 10～15 小时。
- 不进行大规模产品重构，不先重做整站视觉。
- 优先使用已有内容、视频和真实项目素材。
- 默认不依赖广告预算；如果允许，可增加一次小额广告验证。

如果人员、预算或目标市场不同，应该先调整资源配置，而不是直接增加页面数量。

## 3. 目标与非目标

### 目标

90 天内建立一条可重复的增长链路：

```text
真实项目/问题
    ↓
搜索或内容分发
    ↓
项目页或场景页
    ↓
下载 FlyEnv
    ↓
GitHub、安装、反馈或再次访问
```

具体目标不是承诺某个流量数字，而是完成以下验证：

1. 能区分品牌流量、非品牌搜索和低质量 Direct 流量。
2. 能确认哪些项目主题获得展示、点击和下载。
3. 至少跑通 3 个真实项目页的“访问 → 下载”链路。
4. 建立“继续扩展 / 修改 / 停止”的数据规则。

### 非目标

- 不一次性生成 20～100 个相似 SEO 页面。
- 不为了关键词堆砌 FAQ、Schema 或工具页。
- 不因为两周没有排名就删除真实内容。
- 不把“支持某个模块”误认为“拥有该模块的搜索流量”。

## 4. 为什么采用组合方案

| 方案 | 优点 | 风险 | 结论 |
|---|---|---|---|
| 只做 SEO 内容矩阵 | 长期资产，成本相对低 | 反馈慢，容易盲目生产 | 不单独采用 |
| 只做广告和社媒 | 几天内能看到点击和转化 | 停止投入后流量消失 | 只作为验证工具 |
| SEO + 转化 + 分发 + 小额验证 | 既有即时信号，又能形成长期资产 | 需要持续记录和复盘 | **采用** |

## 5. 三个验证时钟

### 0～7 天：即时信号

关注：

- 下载按钮点击
- GitHub 点击
- 视频播放和外部链接点击
- 页面参与时间、滚动深度
- 社区/视频/邮件带来的访问
- Search Console 是否开始出现页面展示

### 2～6 周：内容信号

关注：

- 页面是否被索引
- 哪些查询词带来展示
- 标题和摘要 CTR
- 项目页是否被内部链接和外部渠道发现
- 项目页到下载页的路径

### 6～12 周：SEO 结果

关注：

- 非品牌词排名
- 项目页自然流量
- 项目页下载转化
- 哪些主题值得扩展成内容集群

## 6. Phase 0：第 1 周，建立基线

### 6.1 统一 GA4 事件

建议使用以下事件名：

```text
download_click
github_click
project_cta_click
video_play
license_view
outbound_click
```

每个事件至少记录：

```text
page
page_type
project
locale
os
source
campaign
```

重点不是增加更多埋点，而是让每次点击都能回答：哪个页面、哪个项目、哪个来源带来了动作。

### 6.2 清理流量口径

每周同时查看：

- 品牌词 / 非品牌词
- Direct / Organic / Referral
- 首页 / License / Guide / Project
- 国家、设备、参与时间和下载行为

新加坡、印尼、中国等地区不能仅按用户数判断价值，必须结合参与时间、页面数、下载和 GitHub 点击判断。

### 6.3 访谈和素材盘点

从 GitHub Issues、Discussions、下载反馈、YouTube 评论中找 5～10 位真实用户，回答：

1. 为什么下载 FlyEnv？
2. 下载前搜索了什么？
3. 最后为什么使用或放弃？

同时盘点现有素材：

- [Laravel 指南](../docs/guide/run-laravel-use-flyenv.md)
- WordPress / Node.js / Python / Go 指南
- ERPNext、Gitea 等实录视频
- Docker、XAMPP、Laragon 相关比较内容

输出一页“用户问题—搜索表达—FlyEnv 解决方式”表格。

## 7. Phase 1：第 2～3 周，先优化现有流量

### 7.1 首页只做微创调整

第一层定位统一为：

> FlyEnv is a native local development environment for modern web and full-stack projects.

AI、MCP、数据库、运行时作为能力层，而不是同时作为第一层品类。

首页信息顺序调整为：

1. 它解决什么本地开发问题
2. 可以运行哪些真实项目
3. 一套项目需要哪些服务
4. 为什么选择 Native 而不是 Docker
5. AI Coding + MCP
6. 完整模块列表
7. 下载与 GitHub

### 7.2 增加三个高意图入口

先做：

```text
Run Laravel Locally
Run WordPress Locally
Run Next.js Locally 或 Run ERPNext Locally
```

具体选择以 Phase 0 的素材和数据评分为准。

### 7.3 复用现有 Guide

不重复写同主题文章。现有 [Laravel 页面](../docs/guide/run-laravel-use-flyenv.md) 作为迁移和升级的基础，补充：

- 首屏项目结果
- 技术栈清单
- 视频或截图
- 下载 CTA
- 项目页与相关指南的双向内链

## 8. Phase 2：第 3～8 周，制作 3 个真实项目页

首批只做 3 个，不直接做 20 个。候选优先级：

1. Laravel
2. WordPress
3. Next.js 或 ERPNext

每个页面必须包含：

- 项目是什么、适合谁
- 所需运行时和服务
- Windows/macOS/Linux 的真实差异
- 3～6 步可复现的 FlyEnv 配置流程
- 当前版本真实截图或录屏
- 常见问题和真实踩坑
- 下载 CTA
- 相关指南和视频链接

页面不是“FlyEnv 支持 PHP/Node.js”的模块介绍，而是：

> 用户有一个项目，如何在本地把它跑起来。

## 9. Phase 3：内容发布后的 48 小时分发

每个项目页发布后，固定执行：

- YouTube 视频描述、置顶评论链接回项目页
- GitHub README 或 Discussions 链接
- 一篇社区短帖
- 一个相关开发者社区的实用分享
- 所有外部链接使用 UTM
- 首页、导航、相关 Guide 加内部链接

这样 Google 排名出现之前，也能立刻获得访问和转化反馈。

## 10. 可选的小额广告验证

如果可以投入预算，用约 300～500 美元做短期验证，不追求规模，只测试高意图词：

```text
run laravel on windows
laragon alternative
php development environment windows
run wordpress locally
```

验证内容包括：

- 哪种标题 CTR 高
- 哪种卖点带来下载
- 哪个项目值得继续做 SEO

广告验证过的标题和 CTA，再投入长期内容建设。

## 11. 数据判断规则

| 表现 | 可能原因 | 动作 |
|---|---|---|
| 没有展示 | 未索引或搜索意图不成立 | 检查索引、链接和主题 |
| 有展示、CTR 低 | 标题/摘要不吸引 | 改标题、摘要和首屏 |
| 有点击、停留短 | 页面没有满足意图 | 重写开头和步骤 |
| 停留好、下载少 | CTA 或产品价值不清晰 | 调整 CTA、截图和对比 |

时间规则：

- 14 天内不因没有排名删除真实页面。
- 28 天有展示但 CTR 低，优先修改标题和摘要。
- 6～8 周仍无展示、无外部访问、无转化，再停止扩展该主题。

## 12. 90 天里程碑

### 第 1 个月

- GA4 关键事件可用
- Search Console 与 GA4 建立周报
- 首页完成微创定位调整
- 第一个项目页上线
- 找到 2～3 个有效卖点

### 第 2 个月

- 三个项目页上线
- 每个项目页完成视频、GitHub 和社区分发
- 找到有展示的非品牌搜索词
- 开始优化排名 8～20 位的页面

### 第 3 个月

- 判断哪些主题继续扩展
- 决定是否增加 Docker、Laragon、XAMPP、Herd 迁移页
- 将有效项目页扩展到 5～8 个
- 形成固定的周复盘和月度淘汰机制

## 13. 每周工作节奏

建议固定为：

- 周一：看 GA4 / Search Console / UTM 数据
- 周二：改一页现有内容或 CTA
- 周三：制作一个真实项目内容
- 周四：发布视频、GitHub 和社区分发
- 周五：记录假设、结果和下一步

每个实验必须记录：

```text
假设
改了什么
预期信号
观察周期
实际结果
继续 / 修改 / 停止
```

## 14. 成功标准

90 天后，成功不定义为“流量一定达到某个数字”，而定义为：

1. 知道哪些非品牌搜索词与 FlyEnv 有关。
2. 知道哪些项目页能带来下载。
3. 知道哪些国家和来源是高质量用户。
4. 能用同一模板稳定生产真实项目页。
5. 每个新页面都有明确的继续、修改或停止依据。

最重要的第一步不是继续增加模块，而是先证明：

```text
真实项目需求 → 内容/搜索入口 → FlyEnv 项目页 → 下载
```

这条链路一旦被 2～3 个项目验证，后续 SEO 扩展才有依据。

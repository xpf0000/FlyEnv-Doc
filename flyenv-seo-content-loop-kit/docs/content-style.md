# FlyEnv Content Style

## Voice

Write developer-to-developer.

The tone should be:
- factual
- calm
- practical
- technically specific
- concise where possible
- balanced when comparing products

FlyEnv is maintained by an individual author, so avoid unnecessary corporate "we" language unless the existing site intentionally uses it.

## Avoid marketing filler

Avoid terms such as:
- revolutionary
- ultimate
- game-changing
- best-in-class
- supercharge
- unlock your potential
- seamless experience
- blazing-fast (unless measured and cited)
- more secure (unless a specific, verifiable mechanism is discussed)

Do not use generic SEO introductions such as:

> PHP is one of the world's most popular programming languages...

Prefer to start with the user problem and FlyEnv's actual workflow.

## Feature-page writing

A Feature page should answer:
- What can I do with this module in FlyEnv?
- How does it fit into a local development workflow?
- What adjacent FlyEnv modules work with it?
- What real project/use cases does it support?
- Where can I learn or see more?

Do not force identical headings onto every Feature page.

## Comparison-page writing

Comparison pages must not be attack pages.
Use balanced framing.

Good:
> XAMPP can still be a straightforward choice for developers who only need a traditional Apache + PHP + MariaDB stack.

Bad:
> XAMPP is outdated and limited.

Each comparison should include:
- where the competitor fits well
- where FlyEnv fits well
- meaningful architectural/workflow differences
- verified limitations only
- a practical selection recommendation

## Claims

Do not state "faster", "lighter", "safer", "easier", or "better" as objective facts unless the page provides verifiable evidence or clearly frames them as workflow differences.

## Word count

There is no minimum word count.
Stop when the search intent and product capability are adequately covered.
A 700-word page with specific, useful information is better than a 2,000-word page padded with generic explanation.
